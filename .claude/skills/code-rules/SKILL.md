# Yomi コード規約

セルフレビューで**実際に出た指摘**を蓄積したルール集。
一般論は書かない。この設計で繰り返し間違えたこと、間違えそうなことだけを書く。

## 使い方

- **コードを書く前**: 該当領域のルールに目を通す
- **セルフレビューの最後**: 全ルールに違反がないか照合する
- **新しい指摘が出たら**: 下の「ルールの追加手順」に従って追記する

## ルールの追加手順

セルフレビュー（`self-review` skill）で指摘が出たら、以下を判定する。

1. **その指摘は再発しうるか？** 単発のタイプミスなら追加しない
2. **既存ルールでカバーできるか？** できるなら既存ルールに例を追記する
3. 追加するなら該当カテゴリに、次の形式で書く

```
### R-<カテゴリ略号><連番>. <一行で言い切る禁止 / 必須事項>

**理由**: なぜこれが問題になるのか（このプロジェクト固有の事情で）
**悪い例 / 良い例**: 実際に指摘されたコードを最小化して載せる
**初出**: PR #<番号>
```

ルールは**言い切る**。「なるべく」「可能なら」と書かない。例外があるならその条件を書く。

## SEC — セキュリティ

### R-SEC1. URL・タイトル・メモ・本文を外部に送信しない

**理由**: Yomi は閲覧履歴という機微情報を端末内に持つ。外部送信先は PostHog（匿名イベント）と RevenueCat（購入情報）のみと PRD で宣言しており、プライバシーポリシーにもそう書く。逸脱は約束違反になる。

**必須**: PostHog に送ってよいのは `docs/DesignDoc.md` §7.3 の表にあるイベントとプロパティのみ。表にないプロパティを足すときはポリシーの記載も同時に更新する。

```ts
// 悪い
analytics.capture('item_read', { url: item.url, title: item.title });
// 良い
analytics.capture('item_read', { days_since_saved: diffDays });
```

**初出**: 設計時（`docs/DesignDoc.md` §7.3）

### R-SEC2. 外部由来の文字列を信頼しない

**理由**: 共有された URL、OGP / oEmbed のレスポンス、インポートの貼り付けテキストはすべて攻撃者が制御しうる。

**必須**:
- SQL は必ずプレースホルダ / Drizzle のクエリビルダで組む。文字列連結しない
- HTML の fetch は先頭 256KB で打ち切る
- `new URL()` は必ず try/catch し、失敗を戻り値で表現する（例外を投げっぱなしにしない）
- FTS5 の MATCH にユーザー入力を素通しせず、メタ文字を無害化する

**初出**: 設計時（`docs/DesignDoc.md` §5.2, §5.5）

### R-SEC3. 秘密鍵をリポジトリに置かない

**理由**: Dev override は Ed25519 の署名検証で成立している。秘密鍵が漏れれば誰でも Pro になる。

**必須**: アプリに埋め込むのは**公開鍵のみ**。秘密鍵は 1Password に保管。テスト用の鍵ペアは本番と別に生成し、テストコード内に閉じる。

**初出**: 設計時（`docs/DesignDoc.md` §5.3）

### R-SEC4. 検証の失敗を「通す」方向にフォールバックしない

**理由**: 署名検証・期限チェック・上限判定は、例外時に安全側（拒否）へ倒す。

```ts
// 悪い — 例外で Pro になる
try { return verify(code); } catch { return true; }
// 良い
try { return verify(code); } catch { return false; }
```

**初出**: 設計時

## ARCH — モジュール境界

### R-ARCH1. `share-extension/` は `db/` と `domain/url/` しか import しない

**理由**: iOS の Share Extension はメモリ上限 ~120MB、起動から終了まで 2 秒以内という制約がある。依存が増えるとバンドルサイズと起動時間が悪化し、この制約を破る。

**必須**: RevenueCat / PostHog / Sentry / `features/` を import しない。ESLint の `no-restricted-imports` で機械的に落とす。

**初出**: 設計時（`docs/DesignDoc.md` §3.1）

### R-ARCH2. Share Extension でネットワークアクセスをしない

**理由**: 同上。メタ取得は本体側の MetaFetchWorker が担う。

**初出**: 設計時（`docs/DesignDoc.md` 設計原則 2）

### R-ARCH3. 画面から DB を直接触らない

**理由**: クエリが画面に散ると、インデックス設計の変更やパフォーマンス改善の影響範囲が読めなくなる。

**必須**: 読み書きは `src/db/repositories/` を経由する。画面は Repository と React Query のフックだけを見る。

**初出**: 設計時（`docs/DesignDoc.md` §3.1）

### R-ARCH4. RevenueCat を `useEntitlement()` 以外から参照しない

**理由**: Pro 判定の分岐が散ると、Dev override との整合が取れなくなり、上限判定にも抜けが出る。

**初出**: 設計時（`docs/DesignDoc.md` 設計原則 4）

### R-ARCH5. 状態を `unread / read / archived` の 3 つから増やさない

**理由**: 状態が増えるとリスト・集計・遷移の組み合わせが指数的に増える。「あとで」はスヌーズ（`snoozedUntil`）で表現し、status は `unread` のまま保つ。

**初出**: 設計時（`docs/DesignDoc.md` 設計原則 3, §4.2）

## DB — データアクセス

### R-DB1. 状態を変える書き込みは必ず `read_logs` に追記する

**理由**: Stats は `items` の現在値ではなく `read_logs` の履歴から集計する。追記が漏れると週次集計が過小になり、読了 → 未読に戻す操作で履歴が消える。

**必須**: `markRead` / `archive` / `restoreToUnread` / 保存 のすべてで追記する。Repository の内側で行い、呼び出し側に任せない。

**初出**: 設計時（`docs/DesignDoc.md` §4.1）

### R-DB2. 複数行の更新は 1 トランザクションで行う

**理由**: 一括アーカイブ・一括インポートが途中で失敗すると、部分適用された中途半端な状態が残る。

**初出**: 設計時（`docs/DesignDoc.md` §5.7）

### R-DB3. 保存上限のカウントから `archived` を除く

**理由**: アーカイブはゴミ箱相当。カウントに含めると、捨てたのに上限に当たるという理不尽な挙動になる。

**初出**: 設計時（`docs/PRD.md` §7.5）

## UI — 画面・デザイン

### R-UI1. 色・角丸・フォントをコンポーネント内にハードコードしない

**理由**: ダークモードとソースカラーの割り当てがトークン前提で設計されている。ハードコードするとダークで破綻する。

**必須**: `src/ui/tokens.ts` または Tailwind のトークンを使う。SVG / Skia からも `tokens.ts` を参照する。

**初出**: 設計時（`docs/DesignGuideline.md` §10）

### R-UI2. 色カードに影を付けない。ノッチは Today's Pick 以外に使わない

**理由**: 影付きの色カードは浮きすぎる。ノッチはアプリのシグネチャで、多用すると効かなくなる。1 画面に 1 つだけ。

**初出**: 設計時（`docs/DesignGuideline.md` §6, §9）

### R-UI3. コピーは動詞で、煽らない

**理由**: 「読み切る」ことを支援するアプリであり、焦らせるアプリではない。

**必須**:
- ボタンは動詞（「保存」「開く」「読んだ」「あとで」「アーカイブ」）。「OK」「送信」を使わない
- Pro の誘導は事実だけ（「残り 5 件」）。「今すぐアップグレード！」と書かない
- 数値に感嘆符・絵文字を付けない。ストリーク / バッジ / 紙吹雪を作らない

**初出**: 設計時（`docs/DesignGuideline.md` §7, §9）

### R-UI4. リストは仮想化し、`contentInset.bottom = 100` を入れる

**理由**: 5,000 件で 500ms 以内という要件がある。またタブバーが浮いているため、入れないと最後の行が隠れる。

**初出**: 設計時（`docs/PRD.md` §8, `docs/DesignGuideline.md` §5）

## TEST — テスト

### R-TEST1. pure function にはテストを書く

**理由**: URL 正規化・パーサ・署名検証・`pickToday` は、間違えても画面上は静かに壊れる。実機確認では気づけない。

**必須**: 正常系だけでなく境界値と異常系を書く。ネットワークに出ず、フィクスチャを使う。

**初出**: 設計時（`docs/DesignDoc.md` §8）

### R-TEST2. バグを直すときは、先に再現テストを書く

**理由**: 再現しない修正は、直ったことを確認できず、再発も検知できない。

**初出**: 設計時

## PROC — 進め方

### R-PROC1. この環境で実機確認はできない。「動作確認済み」と書かない

**理由**: Linux コンテナ上のため iOS ビルド・Share Extension・課金・通知・E2E を実行できない。検証できるのは typecheck / lint / Vitest まで。

**必須**: PR 本文に「未検証（実機確認が必要）」の項を設け、該当項目を列挙する。

**初出**: 設計時

### R-PROC2. 仕様から外れる判断をしたら PR に明記する

**理由**: `docs/` が唯一の仕様。黙って外れると、後からドキュメントとコードのどちらが正しいか分からなくなる。

**必須**: 外れた箇所・理由・ドキュメントを更新すべきかを PR 本文に書く。

**初出**: 設計時

### R-PROC3. フォーマッタ・自動修正をリポジトリ全体にかけない

**理由**: `prettier --write .` を無警戒に実行すると、その PR と無関係な `docs/` や `.claude/` まで書き換わる。とくに日本語の Markdown 表は Prettier が全角文字幅を考慮せず桁揃えするため、見た目が崩れたうえ差分が数百行に膨らみ、レビューで本来の変更が埋もれる。

**必須**:
- Markdown は Prettier の対象外にする（`.prettierignore` に `*.md`）
- 一括自動修正を実行したら、**コミット前に `git status` で意図しないファイルが混ざっていないか確認する**
- PR の差分に、その issue のスコープ外のファイルが含まれていないことを確認する

**初出**: PR #33

### R-PROC4. 脆弱性は「アプリに同梱されるか」で切り分けて判断する

**理由**: `npm audit` の指摘には prebuild / CI でしか動かないツールチェーンのものが混ざる。すべてを一律に扱うと、直せないものに時間を使うか、逆に本当に危険なものを見落とす。

**必須**: high 以上が出たら、まず**実行時に同梱されるか**を確認する。同梱されるなら修正必須。ビルド時のみなら、判断と根拠を PR に書いて記録する（黙って無視しない）。

**初出**: PR #33
