# Yomi コード規約

セルフレビューで**実際に出た指摘**を蓄積したルール集。
一般論は書かない。この設計で繰り返し間違えたこと、間違えそうなことだけを書く。

## 使い方

- **コードを書く前**: 該当領域のルールに目を通す
- **セルフレビューの最後**: 全ルールに違反がないか照合する
- **新しい指摘が出たら**: 下の「ルールの追加手順」に従って追記する

## ルールの追加手順

セルフレビュー（`self-review` skill）で指摘が出たら、以下を判定する。

1. **その指摘は再発しうるか？** 単発のタイプミスなら追加しない
2. **既存ルールでカバーできるか？** できるなら既存ルールに例を追記する
3. 追加するなら該当カテゴリに、次の形式で書く

```
### R-<カテゴリ略号><連番>. <一行で言い切る禁止 / 必須事項>

**理由**: なぜこれが問題になるのか（このプロジェクト固有の事情で）
**悪い例 / 良い例**: 実際に指摘されたコードを最小化して載せる
**初出**: PR #<番号>
```

ルールは**言い切る**。「なるべく」「可能なら」と書かない。例外があるならその条件を書く。

## SEC — セキュリティ

### R-SEC1. URL・タイトル・メモ・本文を外部に送信しない

**理由**: Yomi は閲覧履歴という機微情報を端末内に持つ。外部送信先は PostHog（匿名イベント）と RevenueCat（購入情報）のみと PRD で宣言しており、プライバシーポリシーにもそう書く。逸脱は約束違反になる。

**必須**: PostHog に送ってよいのは `docs/DesignDoc.md` §7.3 の表にあるイベントとプロパティのみ。表にないプロパティを足すときはポリシーの記載も同時に更新する。

```ts
// 悪い
analytics.capture('item_read', { url: item.url, title: item.title });
// 良い
analytics.capture('item_read', { days_since_saved: diffDays });
```

**初出**: 設計時（`docs/DesignDoc.md` §7.3）

### R-SEC2. 外部由来の文字列を信頼しない

**理由**: 共有された URL、OGP / oEmbed のレスポンス、インポートの貼り付けテキストはすべて攻撃者が制御しうる。

**必須**:
- SQL は必ずプレースホルダ / Drizzle のクエリビルダで組む。文字列連結しない
- HTML の fetch は先頭 256KB で打ち切る
- `new URL()` は必ず try/catch し、失敗を戻り値で表現する（例外を投げっぱなしにしない）
- FTS5 の MATCH にユーザー入力を素通しせず、メタ文字を無害化する

**初出**: 設計時（`docs/DesignDoc.md` §5.2, §5.5）

### R-SEC3. 秘密鍵をリポジトリに置かない

**理由**: Dev override は Ed25519 の署名検証で成立している。秘密鍵が漏れれば誰でも Pro になる。

**必須**: アプリに埋め込むのは**公開鍵のみ**。秘密鍵は 1Password に保管。テスト用の鍵ペアは本番と別に生成し、テストコード内に閉じる。

**初出**: 設計時（`docs/DesignDoc.md` §5.3）

### R-SEC4. 検証の失敗を「通す」方向にフォールバックしない

**理由**: 署名検証・期限チェック・上限判定は、例外時に安全側（拒否）へ倒す。

```ts
// 悪い — 例外で Pro になる
try { return verify(code); } catch { return true; }
// 良い
try { return verify(code); } catch { return false; }
```

**初出**: 設計時

## ARCH — モジュール境界

### R-ARCH1. `share-extension/` は `@/db`・`@/domain/url`・`@/design` しか import しない

**理由**: iOS の Share Extension はメモリ上限 ~120MB、起動から終了まで 2 秒以内という制約がある。依存が増えるとバンドルサイズと起動時間が悪化し、この制約を破る。

**必須**: RevenueCat / PostHog / Sentry / `@/ui` / `@/features` を import しない。ESLint の `no-restricted-imports` と `app.config.ts` の `excludedPackages` の両方で落とす。

`@/design`（デザイントークン）は `docs/DesignDoc.md` §3.1 に無いが許可している。値と JSON だけでコンポーネントを引き込まず、`docs/DesignGuideline.md` §8 が Extension にも同じトークンを使うよう求めているため。

**初出**: 設計時（`docs/DesignDoc.md` §3.1）、PR #41 で `@/design` を追加

### R-ARCH2. Share Extension でネットワークアクセスをしない

**理由**: 同上。メタ取得は本体側の MetaFetchWorker が担う。

**初出**: 設計時（`docs/DesignDoc.md` 設計原則 2）

### R-ARCH3. 画面から DB を直接触らない

**理由**: クエリが画面に散ると、インデックス設計の変更やパフォーマンス改善の影響範囲が読めなくなる。

**必須**: 読み書きは `src/db/repositories/` を経由する。画面は Repository と React Query のフックだけを見る。

**初出**: 設計時（`docs/DesignDoc.md` §3.1）

### R-ARCH4. RevenueCat を `src/domain/entitlement/` 以外から参照しない

**理由**: Pro 判定の分岐が散ると、Dev override との整合が取れなくなり、上限判定にも抜けが出る。

**必須**: 画面からは `useEntitlement()` を使う。ESLint の `no-restricted-imports` が `react-native-purchases` の import を `src/domain/entitlement/` 以外で禁止しており、機械的に落ちる。

**初出**: 設計時（`docs/DesignDoc.md` 設計原則 4）、PR #46 で lint による強制を追加

### R-ARCH5. 状態を `unread / read / archived` の 3 つから増やさない

**理由**: 状態が増えるとリスト・集計・遷移の組み合わせが指数的に増える。「あとで」はスヌーズ（`snoozedUntil`）で表現し、status は `unread` のまま保つ。

**初出**: 設計時（`docs/DesignDoc.md` 設計原則 3, §4.2）

## DB — データアクセス

### R-DB1. 状態を変える書き込みは必ず `read_logs` に追記する

**理由**: Stats は `items` の現在値ではなく `read_logs` の履歴から集計する。追記が漏れると週次集計が過小になり、読了 → 未読に戻す操作で履歴が消える。

**必須**: `markRead` / `archive` / `restoreToUnread` / 保存 のすべてで追記する。Repository の内側で行い、呼び出し側に任せない。

**初出**: 設計時（`docs/DesignDoc.md` §4.1）

### R-DB2. 複数行の更新は 1 トランザクションで行う

**理由**: 一括アーカイブ・一括インポートが途中で失敗すると、部分適用された中途半端な状態が残る。

**初出**: 設計時（`docs/DesignDoc.md` §5.7）

### R-DB3. 保存上限のカウントから `archived` を除く

**理由**: アーカイブはゴミ箱相当。カウントに含めると、捨てたのに上限に当たるという理不尽な挙動になる。

**初出**: 設計時（`docs/PRD.md` §7.5）

## UI — 画面・デザイン

### R-UI1. 色・角丸・フォントをコンポーネント内にハードコードしない

**理由**: ダークモードとソースカラーの割り当てがトークン前提で設計されている。ハードコードするとダークで破綻する。

**必須**: `src/ui/tokens.ts` または Tailwind のトークンを使う。SVG / Skia からも `tokens.ts` を参照する。

**初出**: 設計時（`docs/DesignGuideline.md` §10）

### R-UI2. 色カードに影を付けない。ノッチは Today's Pick 以外に使わない

**理由**: 影付きの色カードは浮きすぎる。ノッチはアプリのシグネチャで、多用すると効かなくなる。1 画面に 1 つだけ。

**初出**: 設計時（`docs/DesignGuideline.md` §6, §9）

### R-UI3. コピーは動詞で、煽らない

**理由**: 「読み切る」ことを支援するアプリであり、焦らせるアプリではない。

**必須**:
- ボタンは動詞（「保存」「開く」「読んだ」「あとで」「アーカイブ」）。「OK」「送信」を使わない
- Pro の誘導は事実だけ（「残り 5 件」）。「今すぐアップグレード！」と書かない
- 数値に感嘆符・絵文字を付けない。ストリーク / バッジ / 紙吹雪を作らない

**初出**: 設計時（`docs/DesignGuideline.md` §7, §9）

### R-UI4. リストは仮想化し、`contentInset.bottom = 100` を入れる

**理由**: 5,000 件で 500ms 以内という要件がある。またタブバーが浮いているため、入れないと最後の行が隠れる。

**初出**: 設計時（`docs/PRD.md` §8, `docs/DesignGuideline.md` §5）

## TEST — テスト

### R-TEST1. pure function にはテストを書く

**理由**: URL 正規化・パーサ・署名検証・`pickToday` は、間違えても画面上は静かに壊れる。実機確認では気づけない。

**必須**: 正常系だけでなく境界値と異常系を書く。ネットワークに出ず、フィクスチャを使う。

**初出**: 設計時（`docs/DesignDoc.md` §8）

### R-TEST2. バグを直すときは、先に再現テストを書く

**理由**: 再現しない修正は、直ったことを確認できず、再発も検知できない。

**初出**: 設計時

## PROC — 進め方

### R-PROC1. この環境で実機確認はできない。「動作確認済み」と書かない

**理由**: Linux コンテナ上のため iOS ビルド・Share Extension・課金・通知・E2E を実行できない。検証できるのは typecheck / lint / Vitest まで。

**必須**: PR 本文に「未検証（実機確認が必要）」の項を設け、該当項目を列挙する。

**初出**: 設計時

### R-PROC2. 仕様から外れる判断をしたら PR に明記する

**理由**: `docs/` が唯一の仕様。黙って外れると、後からドキュメントとコードのどちらが正しいか分からなくなる。

**必須**: 外れた箇所・理由・ドキュメントを更新すべきかを PR 本文に書く。

**初出**: 設計時

### R-PROC3. フォーマッタ・自動修正をリポジトリ全体にかけない

**理由**: `prettier --write .` を無警戒に実行すると、その PR と無関係な `docs/` や `.claude/` まで書き換わる。とくに日本語の Markdown 表は Prettier が全角文字幅を考慮せず桁揃えするため、見た目が崩れたうえ差分が数百行に膨らみ、レビューで本来の変更が埋もれる。

**必須**:
- Markdown は Prettier の対象外にする（`.prettierignore` に `*.md`）
- 一括自動修正を実行したら、**コミット前に `git status` で意図しないファイルが混ざっていないか確認する**
- PR の差分に、その issue のスコープ外のファイルが含まれていないことを確認する

**初出**: PR #33

### R-PROC4. 脆弱性は「アプリに同梱されるか」で切り分けて判断する

**理由**: `npm audit` の指摘には prebuild / CI でしか動かないツールチェーンのものが混ざる。すべてを一律に扱うと、直せないものに時間を使うか、逆に本当に危険なものを見落とす。

**必須**: high 以上が出たら、まず**実行時に同梱されるか**を確認する。同梱されるなら修正必須。ビルド時のみなら、判断と根拠を PR に書いて記録する（黙って無視しない）。

**初出**: PR #33

### R-SEC5. URL を受け取ったら http(s) 以外のスキームを弾く

**理由**: `new URL('javascript:alert(1)')` も `new URL('file:///etc/passwd')` も例外を投げずにパースが成功する。スキームを検査しないと、保存されたうえで SFSafariViewController に渡ってしまう。

```ts
// 悪い — javascript: が通る
const u = new URL(raw);
// 良い
if (!new Set(['http:', 'https:']).has(u.protocol)) return null;
```

**初出**: PR #34

### R-SEC6. 正規化で「別物を同一視する」方向の変換を安易に増やさない

**理由**: 正規化は url_hash の一致 = 重複検知に直結する。過剰に落とすと**別々の記事が同じ hash になり、2 件目以降が「保存済み」と誤判定されて保存できなくなる**（ユーザーから見れば保存の失敗）。逆に落とし足りない場合は重複が 1 件増えるだけで済む。

**必須**: 迷ったら**落とさない**方に倒す。ホスト固有のトラッキングパラメータは、そのホストに限定して落とす。

```ts
// 悪い — 一般 Web の /search?s=rails まで消える
if (['s', 't'].includes(key)) del(key);
// 良い
if (hostMatches(host, 'x.com') && ['s', 't'].includes(key)) del(key);
```

**初出**: PR #34

### R-TEST3. 文字列を切り詰める処理には「切ってはいけない入力」のテストを書く

**理由**: 末尾の記号を落とす、長さで打ち切る、といった処理は正常系のテストだけだと通ってしまい、実データで壊れる。`https://ja.wikipedia.org/wiki/Ruby_(プログラミング言語)` のように記号が意味を持つ入力が必ず存在する。

**初出**: PR #34

### R-DB4. `read_logs` から `items` へ外部キーを張らない

**理由**: アーカイブからの物理削除でアイテムが消えても、「その週に読んだ」という事実は Stats の集計に残す必要がある。外部キーを張ると cascade か制約違反のどちらかになり、どちらも履歴が壊れる。

**初出**: PR #36

### R-DB5. 設定値が 2 箇所に必要なときは、片方をテストで固定する

**理由**: App Group（`app.config.ts` と `src/db/appGroup.ts`）のように、ビルド設定とアプリコードの両方が同じ値を必要とすることがある。食い違っても**ビルドは通り**、「共有シートで保存したものが本体に出てこない」といった原因の分かりにくい壊れ方をする。

**必須**: 一元化できないなら、一致を検証するテストを書く（`src/config/appConfig.test.ts` が例）。

**初出**: PR #36

### R-TEST4. スキーマのテストは、生成された実際のマイグレーションを適用して行う

**理由**: テスト用に `CREATE TABLE` を手書きすると、本番に適用される SQL とテストが検証する SQL が別物になり、インデックスや制約の抜けを検知できない。

**必須**: `createTestDb()`（`src/db/testing.ts`）を使う。これは `drizzle/` の実ファイルを drizzle 本来のマイグレータで適用する。ドライバだけが本番と異なる（expo-sqlite は Node で動かないため better-sqlite3）。

**初出**: PR #36

### R-DB6. `sql` テンプレートに値を直接埋め込まない。比較は drizzle の演算子を通す

**理由**: `sql\`...\`` に `Date` や配列をそのまま埋め込むと、カラムの `timestamp` モードによる変換が効かず、実行時に `SQLite3 can only bind numbers, strings, bigints, buffers, and null` で落ちる。**型チェックは通る**ので、テストが無ければ実機で初めて気づく。

```ts
// 悪い — Date がそのまま bind されて落ちる
sql`CASE WHEN ${items.snoozedUntil} > ${now} THEN 1 ELSE 0 END`
// 良い — gt() がカラムの型に合わせて変換する
sql`CASE WHEN ${gt(items.snoozedUntil, now)} THEN 1 ELSE 0 END`

// 悪い
sql`${itemTags.itemId} IN ${itemIds}`
// 良い
inArray(itemTags.itemId, itemIds)
```

`sql` テンプレートを使ってよいのは、カラム参照と値を含まない SQL 片（`CASE WHEN ... THEN 1 ELSE 0 END`、`MAX(...)` など）だけ。

**初出**: PR #37

### R-DB7. 複数件を扱う関数は、一括で引くクエリを用意する

**理由**: リスト描画で 1 行ずつ引くと N+1 になり、5,000 件 / 500ms の要件（`docs/PRD.md` §8）を満たせない。

**必須**: `listForItem`（単数）を作ったら `listForItems`（複数）も用意し、画面はループの中で単数版を呼ばない。空配列を渡されたらクエリを投げずに空を返す。

**初出**: PR #37

### R-TEST5. ネイティブモジュールに依存してテスト不能になったら、シムで切る

**理由**: `expo-crypto` は `react-native` を読み込むため Node で動かず、これを import しているモジュールは**その先の層まで丸ごと**テスト不能になる（Repository 層全体が該当した）。

**必須**: 契約が単純なものは `test/shims/` にシムを置き、`vitest.config.mts` の alias で差し替える。**シムに置き換わっても検証の穴にならないこと**を確認する（実ロジックは乱数源などを引数に取る純粋関数として別途テストする）。

**初出**: PR #37

### R-UI5. トークン・定数のモジュールから `react-native` を import しない

**理由**: `react-native` は Flow で書かれており Node のパーサが読めない。値の定義に混ぜると、そのファイルと**それを import する層まで丸ごと**テスト不能になる（`tokens.ts` に `useColorScheme` を置いて実際にそうなった）。Share Extension から読めなくなる問題もある。

**必須**: 値は `tokens.ts` に、React のフックは `theme.ts` に置く。テーマ解決も `themeColors(scheme)` のような純粋関数にしておき、フックはそれを呼ぶだけにする。

**初出**: PR #38

### R-UI6. 同じ値を 2 箇所が必要とするなら、共通の JSON を両方から読む

**理由**: R-DB5 は一元化できない場合の次善策（テストで固定）だが、**一元化できるならその方がよい**。色は `tailwind.config.js`（CommonJS）と `tokens.ts`（TS）の両方が必要とするが、`src/ui/palette.json` を両方が読むことでドリフト自体が起きない。

**初出**: PR #38

### R-DEP1. ライブラリの内部 `build/` パスから型や実装を import しない

**理由**: expo-router 57 のタブバーの型は `expo-router/build/react-navigation/bottom-tabs/types` にしか公開されていない。内部パスに依存するとバージョン追従で黙って壊れる。

**必須**: 必要な形だけを**構造的な型としてローカルに定義する**。使うプロパティが少ないほど壊れにくい。

**初出**: PR #38

### R-SEC7. 外部 API のレスポンスは型を仮定せず 1 フィールドずつ検証する

**理由**: oEmbed / OGP のレスポンスは仕様変更されうるし、攻撃者が制御するサイトから返ることもある。`payload.html.replace(...)` のように型を仮定すると、`html` が数値や欠落だった場合にクラッシュする。

**必須**: `unknown` で受けて `asString()` のような検証を通す。パース関数は `null` / 文字列 / 数値 / 配列を渡しても例外を投げないこと（テストで固定する）。

**初出**: PR #39

### R-SEC8. レスポンス本文はストリームで読み、上限で打ち切る

**理由**: `response.text()` は本文全体をメモリに載せる。サイズ上限を宣言しないサイトに当たると端末のメモリを食い潰す。

**必須**: `readAtMost(response, MAX_HTML_BYTES)` を使う。上限は 256KB（`docs/DesignDoc.md` §5.2）。

**初出**: PR #39

### R-TEST6. ネットワークを使う処理は fetch を注入してテストする

**理由**: 実際に外部へ出るテストは不安定で遅く、CI で落ちる。かといってテストが無いと、エンドポイントの組み立てミスやエラー分岐の抜けに気づけない。

**必須**: `fetchImpl` を引数で受け取れるようにし、テストではモックを渡す。**エンドポイントの URL・ヘッダ・エラー分岐（http / network / timeout / parse）を個別に検証する**。

**初出**: PR #39

### R-PERF1. 並列処理は固定数のワーカーで queue を消費する。`Promise.all` で全件を同時に投げない

**理由**: `Promise.all(items.map(fetch))` は全件を同時に走らせるため、10 件なら 10 本の接続が同時に開く。逆に逐次処理にすると、1 件のタイムアウト（8 秒）が後続をすべて止める。

export const DEFAULT_TIME_OF_DAY: TimeOfDay = { hour: 8, minute: 0 };
export const DEFAULT_NOTIFICATION_TIME = formatTimeOfDay(DEFAULT_TIME_OF_DAY);

**必須**:
- 翻訳先は `satisfies` で縛る。キーを 1 つ消して**実際にコンパイルエラーになることを確認する**
- 画面のツリーを走査して直書きを検出するテストを置く。**1 箇所わざと戻して落ちることを確認する**
- 走査対象のファイル数が想定以上あることもテストする（パスの typo で 0 件検査が素通りしない）

**初出**: PR #60

### R-I18N3. 複数形しか定義が無いキーは、`count` が無くても本文に倒す

**理由**: `key_one` / `key_other` だけを定義したキーを `t('key')` と引くと、素通りしてキー文字列がそのまま画面に出る。型は通り、テストを書くまで気づかない。

```ts
// 悪い — count が無いと key のまま返り、画面に "item.daysAgo" と出る
if (typeof count !== 'number') return key;
// 良い
if (typeof count !== 'number') return has(key) ? key : `${key}_other`;
```

**必須**: 複数形キーを `count` 無しで引くテストを置く。

**初出**: PR #60

### R-I18N4. 法務文書は i18n のキーに割らず、言語ごとに 1 つの文書として持つ

**理由**: 条項を `legal.terms.section3.item2` のような細かいキーに分けると、**文書として通して読めなくなり、法的な見直しができない**。一方で放置すると、片方の言語にだけ条項がある状態に気づけない。

**必須**: `features/legal/{ja,en}/` に言語ごとの文書を置く。そのうえで、**日英で節の数とブロック構成が一致する**ことをテストで固定する。

**初出**: PR #60

### R-I18N5. 設定に依存する値は、Extension へ App Group 経由で渡す

**理由**: Share Extension は本体の MMKV を読めない。言語やテーマのような「本体で選んだ設定」は、本体が解決した結果を共有ファイルに書いて渡すしかない。渡さないと、アプリ内で英語にしても共有シートだけ日本語、という食い違いになる。

**必須**: 共有状態の書き手が 2 つ以上になったら、**読んでから混ぜる**。丸ごと上書きすると、あとから書いた方がもう片方を消す。

```ts
export function updateSharedState(patch: Partial<SharedState>): void {
  writeSharedState({ ...readSharedState(), ...patch });
}
```

**初出**: PR #60

### R-UI19. 設定が実際に効いていることを、設定を追加した時点で確認する

**理由**: 設定画面に「テーマ」の行があり、MMKV への保存も動いていたのに、**読む側が誰もいなかった**。`useThemeColors()` は端末設定しか見ておらず、選んでも何も変わらない状態が残っていた。UI を先に作ると、結線されていないことに気づけない。

**必須**: 設定値を追加したら、**読む側を同じ PR で書く**。加えて、端末設定に追従する仕組み（`StatusBar style="auto"`、NativeWind の `dark:`、ナビゲーションの既定色）が別経路で残っていないか探す。1 箇所でも取りこぼすとそこだけ設定を無視する。

**初出**: PR #58

### R-UI20. iOS では影とクリッピングを同じ View に載せない

**理由**: `overflow: 'hidden'` は iOS で `clipsToBounds` になり、**バウンズの外に描かれる影ごと切り落とす**。さらに影はレイヤーの不透明部分から作られるので、背景色を持たない View に影だけ指定しても何も描かれない。両方を満たすには 2 枚に分け、**塗りと影を外側、クリッピングを内側**に置く必要がある。

`Card` が 1 枚に両方を載せていたため、設定画面・Stats・アイテム詳細を含む**アプリ内の白カードすべてで影が出ていなかった**。型もテストも通り、実機で並べて見るまで気づけない。

```tsx
// 悪い — 影が出ない
<View style={{ borderRadius, backgroundColor, overflow: 'hidden', ...shadow }} />
// 良い
<View style={{ borderRadius, backgroundColor, ...shadow }}>
  <View style={{ borderRadius, overflow: 'hidden' }}>{children}</View>
</View>
```

**初出**: PR #62

### R-UI21. 高さが中身任せの親の中で `flex: 1` を使わない

**理由**: React Native の `flex: 1` は `flexBasis: 0` を含む。親の高さが子の内容で決まる場合、子の基準サイズが 0 になり**高さごと潰れる**。

`Card` の内側に `flex: 1` を付けようとして、設定行・タグ行・URL カードなど「高さが中身任せ」のカードを全部消すところだった。伸ばしたいのは**親が明確な高さを持つ場合だけ**。

**必須**: 伸ばす必要があるなら、`flex` は親の高さが確定している側（行の中で `alignItems: 'stretch'` が効いている要素など）に付ける。中身任せの箱には `minHeight` を使う。

**初出**: PR #62

### R-UI22. 画面の上端は自分でセーフエリアを空ける

**理由**: ナビバーを使わない設計なので、`paddingTop` を固定値にすると**ノッチのある端末で見出しがステータスバーの下に潜る**。ホーム画面だけ `paddingTop: 24` のままで、他の全画面は `insets.top + 8` を使っていた。1 画面だけずれていても、他を見ている限り気づけない。

**必須**: 最上位のスクロール領域は `paddingTop: insets.top + 8` で揃える。固定値を書かない。

**初出**: PR #62

### R-UI23. Modal の中の入力欄はキーボードを避けない

**理由**: `Modal` は `KeyboardAvoidingView` を持たない。下端に固定した bottom sheet に入力欄を置くと、**入力欄もボタンもキーボードの下に隠れる**。メモシートは `autoFocus` なので、開いた瞬間に何も見えない状態だった。

**必須**:
- 入力欄を持ちうる Modal は `KeyboardAvoidingView`（iOS は `behavior="padding"`）で包む
- 入力欄を含む `ScrollView` には `automaticallyAdjustKeyboardInsets` と `keyboardShouldPersistTaps="handled"` を付ける

**初出**: PR #62

### R-UI24. 固定高のボタンに翻訳されるラベルを入れない

**理由**: 英語のラベルは日本語より長い。「通知を許可して始める」は 10 文字だが "Allow notifications and start" は 29 文字で、幅の狭い端末では 2 行になる。`height` 固定だと**2 行目が切れる**。

**必須**: `height` ではなく `minHeight` を使い、`paddingVertical` と `numberOfLines` を添える。行内に並べる可変長テキストには `flex: 1` を与える。

**初出**: PR #62

### R-UI25. しきい値を文言に直書きしない

**理由**: 「30 日以上放置」「直近 8 週」の数字を文言に埋め込むと、`STALE_THRESHOLD_DAYS` を変えたときに**一覧の中身と見出しがずれる**。ずれても型もテストも通る。

**必須**: `{days}` のような差し込みで受け、呼び出し側が定数を渡す。文言が数字を直書きしていないことをテストで固定する。

**初出**: PR #62
