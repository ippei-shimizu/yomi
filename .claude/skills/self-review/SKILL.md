# セルフレビュー

Yomi の PR をマージする前に、必ずこの手順で差分を検査する。
**セキュリティ観点は毎回必ず実行する**（他観点は差分に該当がなければスキップ可）。

## 進め方

1. `git diff origin/main...HEAD` で差分**全体**を読む。ファイル単位ではなく変更セット全体として読む
2. 下の 5 観点を順に当てる。観点ごとに「該当なし」ではなく、**何を確認して該当なしと判断したか**を言えるようにする
3. 見つけた指摘を重大度で分類する（下記）
4. **Blocker / Major は修正してから**再度 1 に戻る。Minor は判断のうえ修正するか issue 化する
5. `.claude/skills/code-rules/SKILL.md` に照らして違反がないか確認する
6. 今後も繰り返しそうな指摘は `code-rules` にルールとして追記する（`code-rules` skill の手順に従う）

## 重大度

| 区分 | 定義 | 扱い |
|---|---|---|
| **Blocker** | 情報漏洩・データ破壊・クラッシュ・審査リジェクトに直結する | 修正必須。マージ不可 |
| **Major** | 仕様との不一致、明確なバグ、実測で問題になるパフォーマンス劣化 | 修正必須。マージ不可 |
| **Minor** | 可読性・命名・軽微な重複。動作に影響しない | 修正するか issue 化 |
| **Nit** | 好みの範囲 | 記録のみ |

「たぶん大丈夫」は Major として扱う。確認していないものを Minor に落とさない。

---

## 観点 1: セキュリティ（必須）

Yomi は**端末内に閲覧履歴という機微情報を持つ**アプリであり、課金と App Extension を含む。以下は毎回確認する。

### 秘密情報
- [ ] API キー・秘密鍵・トークンがリポジトリに含まれていないか（`git diff` に `key`, `secret`, `token`, `-----BEGIN` が現れたら必ず中身を確認）
- [ ] Ed25519 の**秘密鍵**が混入していないか。アプリに埋め込んでよいのは公開鍵のみ
- [ ] `.env` や認証情報が `.gitignore` されているか
- [ ] ログ・クラッシュレポートに秘密情報が出力されていないか

### プライバシー（Yomi 固有・最重要）
- [ ] **URL・タイトル・メモを外部送信していないか**。PostHog に送ってよいのは匿名イベントとその定義済みプロパティのみ（`docs/DesignDoc.md` §7.3）
- [ ] Sentry のイベント・breadcrumb に URL やタイトルが載っていないか
- [ ] `console.log` に URL やメモが出ていないか（本番ビルドで残る）
- [ ] プライバシーポリシーの記載と実際の送信内容が一致しているか

### 入力の扱い
- [ ] 外部由来の文字列（共有された URL、OGP/oEmbed のレスポンス、インポートの貼り付けテキスト）を**信頼していないか**
- [ ] SQL を文字列連結で組み立てていないか。必ずプレースホルダ / Drizzle のクエリビルダを使う
- [ ] FTS5 のクエリにユーザー入力をそのまま渡していないか（MATCH 構文はメタ文字を持つ。エスケープするか引用符で囲う）
- [ ] `new URL()` の例外を握りつぶしていないか。不正な URL でクラッシュしないか
- [ ] HTML パース時に**サイズ上限（256KB）**が効いているか。上限なしの fetch は DoS になる
- [ ] リダイレクトの追跡に上限があるか。`file://` や内部アドレスへのリダイレクトを拒否しているか（SSRF）
- [ ] 正規表現に catastrophic backtracking の危険がないか（インポートの URL 抽出は入力長が大きい）

### 認証・課金
- [ ] Pro 判定が `useEntitlement()` 一箇所に集約されているか。他所で RevenueCat を参照していないか
- [ ] Dev override の署名検証が**検証成功時のみ**通っているか。例外時に `true` へフォールバックしていないか
- [ ] `exp`（期限）を検証しているか
- [ ] Keychain（`expo-secure-store`）に置くべきものを MMKV / AsyncStorage に置いていないか

### Share Extension
- [ ] **ネットワークアクセスを行っていないか**（設計上の禁止事項）
- [ ] RevenueCat / PostHog / Sentry を import していないか
- [ ] App Group 経由で共有する値に機微情報が含まれていないか

### 依存関係
- [ ] 新規追加した依存にメンテナンス状況の懸念がないか。同等の機能が既存依存にないか
- [ ] `npm audit` の結果に high 以上が増えていないか

---

## 観点 2: 正しさ

- [ ] **仕様との一致**: 対応する issue と `docs/` の記述に照らして、実装が仕様通りか。仕様から外れる判断をしたなら PR に明記したか
- [ ] 境界値: 0 件、1 件、上限ちょうど（50 件 / タグ 3 個）、上限 +1 の挙動
- [ ] 日時: タイムゾーン、週の起点（**月曜固定**）、日付境界（23:59 → 00:00）
- [ ] 状態遷移が `unread / read / archived` の 3 状態から逸脱していないか。`snooze` で status を変えていないか
- [ ] 状態を変える書き込みで `read_logs` への追記が漏れていないか
- [ ] エラーパス: 失敗時に握りつぶしていないか。ユーザーに回復手段があるか
- [ ] 非同期の競合: 同じレコードへの並行更新、アンマウント後の `setState`
- [ ] トランザクション境界: 複数行の更新が部分適用されないか

---

## 観点 3: パフォーマンス

- [ ] **N+1 クエリ**がないか。リスト描画のたびに 1 件ずつ引いていないか
- [ ] クエリがインデックスを使うか（`idx_items_status_saved` / `idx_items_meta_status` / `idx_read_logs_at`）
- [ ] 長いリストが仮想化されているか。5,000 件で 500ms 以内の要件を満たすか（`docs/PRD.md` §8）
- [ ] `useMemo` / `useCallback` の不足による再レンダリング。逆に不要な memo 化で読みにくくなっていないか
- [ ] 大きなデータを一度にメモリへ載せていないか（エクスポート 5,000 件、HTML fetch）
- [ ] 入力のたびに走る処理（インポートのプレビュー計算、検索）にデバウンスがあるか
- [ ] Share Extension の起動が **2 秒以内**を維持できるか。重い import を増やしていないか
- [ ] 画像のサイズ・キャッシュが適切か

---

## 観点 4: 保守性・設計

- [ ] **モジュール境界**（`docs/DesignDoc.md` §3.1）を守っているか。`share-extension/` が `db/` と `domain/url/` 以外を import していないか
- [ ] 画面から DB を直接叩いていないか。必ず `repositories/` を経由しているか
- [ ] 色・サイズをコンポーネント内にハードコードしていないか。`ui/tokens.ts` / Tailwind トークンを使っているか
- [ ] 命名が周囲のコードと揃っているか。既存の語彙（`unread`, `stale`, `pick`）を再利用しているか
- [ ] 重複: 既存の関数で足りるものを再実装していないか
- [ ] 過剰な抽象化をしていないか。使う場所が 1 つしかない抽象を作っていないか
- [ ] 型: `any` / 不要な `as` / non-null assertion (`!`) を増やしていないか
- [ ] 死んだコード・コメントアウトされたコードを残していないか
- [ ] コメントの密度が周囲と揃っているか。**何をしているか**ではなく**なぜそうしたか**を書いているか

---

## 観点 5: テスト

- [ ] `docs/DesignDoc.md` §8 の方針に沿ったテストがあるか
  - pure function（URL 正規化、パーサ、署名検証、pickToday）→ Vitest 必須
  - Repository → in-memory SQLite で Vitest
- [ ] **バグを修正したなら、そのバグを再現するテストを先に足したか**
- [ ] テストが実装の写しになっていないか（同じロジックを 2 回書いても検証にならない）
- [ ] 異常系・境界値のテストがあるか。ハッピーパスだけになっていないか
- [ ] テストがネットワークに出ていないか（フィクスチャを使う）
- [ ] `npm run lint` / `npm run typecheck` / `npm run test` がすべて通るか

---

## この環境での検証の限界（必ず PR に明記する）

Linux コンテナ上のため以下は**実行できない**。「動作確認済み」と書かない。

- iOS シミュレータ / 実機でのビルドと動作確認
- Share Extension の動作確認
- RevenueCat Sandbox の購入フロー
- 通知のスケジュールと発火
- Maestro E2E

検証できるのは typecheck / lint / Vitest まで。**実機確認が必要な項目は PR 本文に「未検証」として列挙する**。

## 報告の形式

セルフレビューの結果は PR にコメントとして残す。

```
## セルフレビュー

### セキュリティ
- 確認した内容 / 指摘

### 正しさ
### パフォーマンス
### 保守性
### テスト

### 修正した指摘
- [Major] ... → 修正内容

### 未検証（この環境で実行不可）
- ...

### 判定
マージ可 / 要修正
```

指摘ゼロの場合も**何を確認したかを書く**。「問題なし」だけで済ませない。
